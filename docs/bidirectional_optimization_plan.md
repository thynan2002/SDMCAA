## 一、诊断摘要（8×3×3 评测时期）

### 评测体系问题

| 问题 | 影响 |
|------|------|
| 24 个用例仅 12 个有数值金标准，多靠 checklist + Judge 主观评分 | 评测结果不被领域专家认可 |
| 反事实 direction 金标准是过程词，不验证结果方向 | 反事实能力无法被真正评测 |
| 效率指标基准偏向单次调用系统 + 简单 QA 用例占比高 | 总分排名 bare > multi，无法凸显多智能体价值 |
| 阵型/攻防转换/传球网络等战术维度无对应评测 | 战术分析能力无法被衡量 |
| Judge 与被测系统同一模型 | 主观分可信度受质疑 |

### 系统能力问题

| 问题 | 影响 |
|------|------|
| "多智能体"实为多角色串行流水线，Agent 间无协作 | 对比单智能体差异化优势不明显 |
| MCTS 只建模主体球员，对手/队友为启发式 | 反事实分析深度不足 |
| 战术分析依赖 LLM 主观判断，缺 xG/xT/VAEP/PPDA 量化 | 战术分析不专业、不可信 |
| LangGraph 单向 DAG，无自我反思回路 | 输出质量天花板低 |
| MemoryStore 为字符串摘要，无结构化工作记忆 | 复杂任务协同效率低 |

### 8×3×3 评测关键结论

| 发现 | 根因 |
|------|------|
| bare 0.767 > single 0.716 > multi 0.703 | 简单问答占比高 + 效率指标倾斜 |
| 反事实类 multi 大幅领先（0.874 vs bare 0.577） | MCTS + 工具调用真正解决了编造问题 |
| general_qa 类 bare 领先（0.902 vs multi 0.657） | 简单查询多智能体引入错误 + 工具循环开销 |
| 编造数据是头号失败模式（30 次） | 反事实类 bare/single 都在编造 |
| multi 稳定性最低（0.234 vs bare 0.415） | 流水线越长方差越大 |

## 三、未实施建议（后续路线）

### 建议 2.2：MAMCTS 多智能体博弈反事实引擎（影响很高，难度很高，P2）

- 单智能体 MCTS → 双方多智能体博弈搜索（PIMC/ISMCTS，Self-Play 行为模型）
- 反事实场景扩展：战术调整 / 对手应对 / 球员替换，输出概率分布 + 置信区间
- 评测侧：Brier Score 概率校准度、反事实一致性（JS 散度）、场景复杂度分级
- 当前替代：方向性 + checklist + stability 诊断（见 [eval.md](eval.md)）

### 建议 1.4：双 Judge 制 + 效度保障（影响中，难度中，P2）

- 第二独立 Judge 模型 + 分歧仲裁；位置互换盲评 + 双 Judge 一致性常态化
- 当前替代：单 Judge（deepseek-v4-pro）+ 正逆序差一致性指标

### 建议 3.2：系统可扩展性（影响中，难度中高，P2）

- 插件化 Agent 接口（`run(input_state, blackboard) -> output_state`）、工具市场、多数据源适配层（StatsBomb JSON/Opta XML/自定义 CSV）、模型抽象层

### 建议 3.3：可解释性与可视化增强（影响中，难度中，P3）

- 推理路径 + 证据卡片；传球网络/热力图/xT 网格/反事实对比视图；不确定性可视化

### 建议 3.4：部署成本与资源效率（影响中低，难度中，P3）

- 动态模型路由（小模型做结构化决策）、结果缓存层、流式输出优化、Docker 部署 + 水平扩展

## 四、预期收益汇总

| 维度 | 当前状态 | 优化目标 | 提升幅度 |
|------|---------|---------|---------|
| **评测领域真实性** | 50% 程序化金标准，无对标 | 80%+ 程序化，对齐 StatsBomb 指标体系 | 量化指标占比 +60% |
| **多智能体优势（总分）** | multi 垫底 (0.703) | multi 第一，领先 10%+ | 排名反转 + 显著优势 |
| **反事实分析能力** | 方向关键词形同虚设 | 概率校准 + 多场景 + 多智能体博弈 | 领先优势从 30% → 50%+ |
| **鲁棒性区分度** | 全员满分，无区分 | 多维鲁棒性，multi 显著领先 | 编造率 -60% |
| **评测效率** | 全量 ~2 小时+ | 分层评测，L2 < 15 分钟 | 迭代速度 ×2 |
| **输出可解释性** | 纯文字 + 简单 trace | 证据卡片 + 推理路径 + 战术可视化 | 信任度评分 +30% |
| **系统可扩展性** | 硬编码流水线 | 插件化架构 + 工具市场 | 新 Agent 开发成本 -70% |
| **运营成本** | 单模型全量调用 | 动态路由 + 缓存 | LLM 成本 -40% |

## 五、风险与应对

| 风险 | 可能性 | 影响 | 应对措施 |
|------|--------|------|---------|
| MAMCTS 复杂度太高，延期 | 中 | 高 | 先做 5v5 简化版，验证价值后再扩展到 11v11 |
| 双 Judge 成本过高 | 中 | 中 | 先对 20% 用例做双 Judge，验证一致性后再决定是否全量；或者用一个更强的模型做 Judge |
| 辩论机制反而降低质量 | 低 | 中 | 加质量门控，辩论后质量不升则返回初稿；设置最大辩论轮次 |
| 领域指标实现难度大 | 低 | 中 | 先用简化版实现（如 16×8 xT 网格），后续迭代精细化 |
| 用例扩展导致评测时间过长 | 中 | 低 | 分层评测 + 智能选样 + 并行执行 |
| Judge 评分偏差导致结论不可信 | 中 | 高 | 双 Judge 制 + 人工抽检校准 + 一致性指标常态化 |
