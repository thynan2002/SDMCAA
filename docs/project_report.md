## 一、项目背景

传统足球比赛分析依赖人工观看录像逐帧统计，费时费力且难以量化。随着运动追踪技术的普及，比赛数据以「球员追踪 CSV + 足球轨迹 CSV」的形式唾手可得，但**数据到结论之间仍存在巨大鸿沟**：原始坐标数据无法直接回答「7 号的跑动风格是什么」「6 号和 7 号谁更积极」「第 90 帧发生了什么」这类业务问题。

本项目构建一个 **LLM 驱动的足球战术分析多智能体系统（Football Agent）**：仅需输入球员追踪数据与足球轨迹数据，即可自动产出专业级比赛解说、球员表现分析与反事实（What-If）推演——例如"如果 7 号在第 3 秒改为直接射门会怎样"。系统以 **function calling（工具调用）** 为架构核心，全链路经 LangGraph 编排，支持 CLI 对话、单次解说与 Web 可视化界面三种使用方式。

## 二、核心挑战

| # | 挑战 | 具体表现 |
|---|------|---------|
| 1 | **LLM 幻觉：数据可信性危机** | LLM 天然存在编造倾向。若直接让模型基于数据"自由发挥"，回答中可能混入不存在的球员、不真实的战术事实与虚假的数据结论——对体育分析这类**结果必须可溯源**的场景，这是致命缺陷 |
| 2 | **结构化决策与自由文本的混合需求** | 流水线中既有「意图路由、战术决策、剧本、MCTS 策略表、质疑判断」等**必须结构化输出**的决策点，又有「解说稿、报告、风格标签」等**自由文本生成**需求。两种模式如何统一、可靠地区分与交付，是架构层面的核心难题 |
| 3 | **外部依赖的可观测与可回归性** | 系统依赖 DeepSeek API，交互链路过长（多智能体、多轮工具循环、流式输出），一旦改动无法快速定位"是哪一步、哪一次调用"出了问题；真实 API 不可复现，回归测试困难，任何重构都冒着破坏既有行为等价性的风险 |
| 4 | **失败处理的健壮性** | 真实环境中网络抖动、API 超时、模型输出格式非法、工具参数错误、数据缺失等异常层出不穷，系统必须在任何一环失败时仍能给出合理降级结果，而不是整体崩溃或静默出错 |
| 5 | **确定性分析能力缺失** | 球员数据、球路事件、帧级事实、反事实轨迹模拟等都是**确定性计算能力**，原始实现中 LLM 需要从内嵌提示词中"推理"这些事实，既不准确也不可扩展 |

## 三、解决方案

### 1. 工具调用（tool_calls）驱动架构：用契约消灭幻觉

- **终止型工具**（`submit_*`）承载全部结构化决策输出：意图路由、战术决策、剧本、MCTS 策略表、质疑判断、语义档位等，由 pydantic v2 定义参数模型并导出 JSON Schema，执行时自动校验，输出即最终答案；
- **数据工具**（`agents/tools/football.py`，6 个）封装确定性分析能力：球路分析、战术事实提取、帧级核验、球员数据查询、反事实模拟——LLM 需要任何外部信息**只能**通过工具获取，数据不足时工具如实返回，从机制上杜绝凭空编造；
- 自研最小工具循环：`tools` 参数经 ContextVar 交换通道透传，支持多轮工具循环与并行 tool_calls，不改变 `call_llm` 传输签名与 harness 钩子，无工具调用时与纯文本接口逐字节等价。

### 2. 双路径统一的输出契约

`call_llm` 保持 `str | None` 返回值：终止型工具提交 → `json.dumps(工具参数)` 复用既有 JSON 解析器；模型直接返回文本 → 走既有文本解析路径。两条路径产出同一解析结果，结构化与自由文本需求统一收敛。

### 3. 统一 Harness 透明包装层

- **三种运行模式**：`passthrough`（生产观测）/ `record`（真实调用 + 录制 golden）/ `replay`（不触网，golden 精确回放，确定性回归）；
- **全链路 Trace**：Span 树记录每次 LLM 请求/响应哈希、工具循环轮次、状态快照；
- **四维回放比对**：LLM 请求序列 / 逐轮输出 / 状态快照 / 文件哈希，保证重构不破坏等价性；CLI 与 Web 共用同一包装层。

### 4. 失败降级链

瞬时故障自动重试 → 工具调用被服务端拒绝自动降级 → 模型输出非法回退到既有规则兜底（关键词路由、启发式决策）→ 持续失败如实上报「模型调用失败，并非数据不足」，每一层都有明确兜底。

### 5. 多智能体编排 + 反事实推演

- 球员追踪流水线：运动分析 → 球互动 → 球路事件 → 对比排名 → 综合决策 → 解说稿，由 LangGraph `StateGraph` 编排；
- 专业分析流水线：数据采集 → 攻防风格建模 → MCTS 反事实推演（默认 300 次模拟，可配置；指定球员在特定时刻改为射门/传球/盘带，推演后续轨迹与胜率变化，可导出轨迹 CSV）→ 报告生成；
- 数据核验：对系统回答提出质疑时，自动回溯原始数据核验并纠正。

## 四、项目结果

### 交付能力

- **输入**：球员追踪 CSV（`frame_num, track_id, x, y, color`）+ 足球轨迹 CSV（`frame_num, x, y, z`），经帧插值与数据融合为统一语料；
- **输出**：专业级比赛解说稿、球员跑动风格分析、球员对比排名、MCTS 反事实推演与轨迹导出、报告生成、数据核验纠错；
- **三种使用方式**：CLI 交互 REPL（中文自然语言提问）、单次解说（`--once` / `--focus`）、Web 可视化（FastAPI + SSE 流式对话 + Canvas 逐帧渲染）。

### 质量保障

| 保障手段 | 内容 |
|---------|------|
| **pytest 全量通过** | 127 个用例全部通过（含工具调用专项：工具循环 / 并行 tool_calls / 失败分类 / 文本回退 / 绑定 / 回放兼容 / 流式增量 / record→replay 工具闭环） |
| **golden 回放回归** | 真实 API 录制的 13 次 LLM 调用（含工具调用轨迹）回归数据集，回放经四维比对（LLM 请求序列 / 逐轮输出 / 状态快照 / 文件哈希）验证当前代码下回放等价，全程不触网 |
| **A/B 同进程对比** | 裸 SessionManager 与 Harness 包装下输出 / 状态快照 / LLM 请求序列完全一致 |
| **兼容性保持** | 重构全程保持旧 golden 兼容、测试 mock 签名兼容、流式语义不变 |

### 架构沉淀

- 工具层：`ToolSpec` / `ToolRegistry` 注册表 + 失败分类（参数非法 / 执行异常 / 数据不足）；
- 可观测性：Span 树 Trace、golden 录制 / 回放 / 快照对比，形成可复用的 LLM 系统回归体系；
- 技术栈：Python 3.12 + LangGraph + DeepSeek（function calling）+ pydantic v2 + MCTS + FastAPI/SSE + NumPy/Pandas。
